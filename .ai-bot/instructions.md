# Project Instructions

This is the osac monorepo. It contains two independently-versioned Go
components, each with its own build/test toolchain. Determine which
component a ticket or PR concerns from its description and the files
involved, then follow that component's section below. If a change spans
both components, apply both sections and validate each independently.

- `fulfillment-service/` — see [fulfillment-service](#fulfillment-service)
- `osac-operator/` — see [osac-operator](#osac-operator)

## fulfillment-service

This is the fulfillment-service: a gRPC server with REST gateway for managing
infrastructure resources (clusters, hosts, compute instances, networking). It
uses PostgreSQL for storage, OPA for authorization, and supports Kubernetes
deployment via Helm.

Two binaries: `fulfillment-service` (server) and `osac` (CLI).

### Validation Commands

Run these commands (from the `fulfillment-service/` directory) to validate
your changes. All must pass before committing.

#### Build

```bash
cd fulfillment-service
go build ./cmd/fulfillment-service
go build ./cmd/osac
```

#### Unit Tests

```bash
cd fulfillment-service
# Run all unit tests (excludes integration tests in it/)
ginkgo run -r internal

# Run a specific package
ginkgo run internal/servers

# Run tests matching a pattern
ginkgo run -r internal --focus="CreateCluster"
```

Do NOT run `ginkgo run -r` (without restricting to `internal`). That triggers
integration tests which require a kind cluster and take a long time.

#### Code Formatting

```bash
cd fulfillment-service
gofmt -s -w .
# Verify no files changed:
git diff --exit-code
```

#### Proto Linting and Code Generation

After editing any `.proto` file under `fulfillment-service/`, always run both:

```bash
cd fulfillment-service
buf lint
buf generate
```

Then verify no generated files changed unexpectedly:

```bash
git diff --exit-code fulfillment-service/internal/api/
```

#### Module Tidying

After editing `fulfillment-service/go.mod`:

```bash
cd fulfillment-service
go mod tidy
```

### Coding Standards

#### Architecture

- Public servers delegate to private servers and add tenant/auth logic.
  `ClustersServer` (public) wraps `PrivateClustersServer` (private).
- Server files use builder pattern: `ClustersServerBuilder` configures dependencies.
- Both public and private server files live in `fulfillment-service/internal/servers/`
  (e.g., `clusters_server.go` + `private_clusters_server.go`).
- Database layer uses `GenericDAO[O Object]` for type-safe CRUD on protobuf messages.
- Resources are stored as JSON-serialized protobuf in a `data` column.
- CEL filter expressions are translated to SQL WHERE clauses via `FilterTranslator`.

#### Testing

- Tests use **Ginkgo v2 + Gomega**.
- Suite setup in `*_suite_test.go` with `BeforeSuite` and `DeferCleanup`.
- `dao.CreateTables[T]()` dynamically creates test schemas.
- Mocks use `go.uber.org/mock` with `//go:generate mockgen` directives.
  Mock files live alongside source (e.g., `attribution_logic_mock.go`).

#### Proto Structure

Protos are split into public and private APIs, under `fulfillment-service/`:

```text
proto/public/osac/public/v1/   - User-facing API (read-heavy, limited write)
proto/private/osac/private/v1/ - Admin/controller API (full CRUD + Signal RPC)
proto/tests/osac/tests/v1/     - Test-only proto definitions
```

Each resource has `<resource>_type.proto` (messages) and `<resource>s_service.proto` (RPCs).
The `SERVICE_SUFFIX` buf lint rule is intentionally excluded in `fulfillment-service/buf.yaml`.

### Files Never to Edit

These files and directories are generated or managed by external tools.
Never edit them manually:

- `fulfillment-service/internal/api/` -- fully generated by `buf generate` from proto files
- `fulfillment-service/go.sum` -- managed by `go mod tidy`
- `fulfillment-service/**/*_mock.go` files -- generated by `mockgen` via `//go:generate` directives
- `fulfillment-service/charts/` and `fulfillment-service/it/charts/` template directories -- Helm templates, not test code
- `fulfillment-service/dist/` -- build artifacts from goreleaser

### Files to Be Cautious With

- `fulfillment-service/proto/**/*.proto` -- changes here cascade to generated code; always run
  `buf lint && buf generate` after editing
- `fulfillment-service/internal/database/migrations/*.up.sql` -- existing migration files must
  never be modified; only add new numbered migration files
- `fulfillment-service/.goreleaser.yaml`, `fulfillment-service/buf.yaml`, `fulfillment-service/buf.gen.yaml` --
  infrastructure config; verify with maintainers before changing

### Pre-commit Hooks

The repo runs pre-commit with hooks covering both components, including
fulfillment-service-specific golangci-lint and buf-lint hooks scoped to
`fulfillment-service/**/*.go` and `fulfillment-service/**/*.proto`.

## osac-operator

### Validation Commands

Before your session ends, run these commands (from the `osac-operator/`
directory) in order and fix all failures. Lint failures block the PR —
this is non-negotiable.

```bash
cd osac-operator
# 1. Regenerate if you touched CRD types (api/v1alpha1/*_types.go)
make manifests generate

# 2. Format, lint, and test
make fmt
make lint
make test
```

If you modified `osac-operator/go.mod`, also run `go mod tidy` (from `osac-operator/`).

If you modified `osac-operator/buf.gen.yaml`, also run `buf generate` (from `osac-operator/`).

### Coding Standards

- **Commit message format**: `OSAC-XXXXX: description of change`
  (Jira key from the ticket, lowercase description).
- **Dual-controller pattern**: Each resource has a resource controller
  (provisioning, lifecycle, finalizers) and a feedback controller (syncs
  state to fulfillment-service via gRPC). When fixing a bug, determine
  which controller is affected — changes to provisioning logic go in
  `{resource}_controller.go`, changes to state-sync logic go in
  `{resource}_feedback_controller.go`.
- **Reconciliation pattern**: Always save `oldStatus := obj.Status.DeepCopy()`
  before reconciliation. Compare with `equality.Semantic.DeepEqual` after.
  Only call `r.Status().Update()` if the status actually changed — otherwise
  you create infinite reconciliation loops.
- **Finalizer convention**: Resource controllers use
  `osac.openshift.io/{resource}-finalizer`. Feedback controllers use
  `osac.openshift.io/{resource}-feedback-finalizer`. Never remove a
  finalizer before cleanup fully completes.
- **Error handling**: Use `client.IgnoreNotFound(err)` for `Get()` calls
  in reconcile — the resource may be deleted between list and get. For
  parent lookups (e.g., Subnet -> VirtualNetwork), requeue with delay
  rather than setting Phase to Failed.
- **Test framework**: Ginkgo v2 + Gomega with `envtest` (real etcd +
  kube-apiserver). Tests live alongside controllers in
  `osac-operator/internal/controller/`. The test suite in `suite_test.go`
  bootstraps envtest with CRDs from `config/crd/bases` and `config/crd/fakes`.
- **Kubebuilder markers**: Use `+kubebuilder:validation:Required`,
  `+kubebuilder:validation:Pattern`, `+kubebuilder:validation:Enum`,
  `+kubebuilder:printcolumn` in type definitions.
- **AAP integration**: Networking controllers use
  `provisioning.RunProvisioningLifecycle()` with `OnSuccess`, `OnFailed`
  callbacks. Subnet dual-dispatch (fabric + k8s manager) uses
  `RunMultiTargetProvisioningLifecycle()` / `RunMultiTargetDeprovisioningLifecycle()`
  instead, driving one `JobTarget`/`DeprovisionTarget` per manager in parallel.
  Template names follow `{prefix}-{action}-{kind}` (e.g., `osac-create-subnet`).
- **Linter config**: golangci-lint v2 with `osac-operator/.golangci.yml`. Key enabled
  linters: dupl, errcheck, ginkgolinter, goconst, gocyclo, govet,
  ineffassign, lll, misspell, prealloc, revive, staticcheck, unconvert,
  unused. errcheck is relaxed in test files.
